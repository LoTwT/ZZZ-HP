> **配套 Spec**：[求解链路性能规格](../specs/solve-chain-performance.md)（下称「Spec」）。
> **定位**：Spec 定义「结果必须长什么样」，本文定义「按什么顺序做出来」。凡涉及结果形态（目标行为、约束、验收判据、预期收益）的内容，本文**只引用 Spec 条款编号**，不复制原文；Spec 变更后本文无需跟改。
> **纪律**：本文不新增 Spec 之外的命名、接口、字段与格式。发现 Spec 缺口一律记入 §4 并停下来问，不在本文里替它补。
> **状态**：待 Owner 确认 §1 与 §4 后开工。本文是活文档：执行中拆步/合步/换序直接改，只有「范围」变化才回来重写。

## 0. 执行顺序一览（与排序理由）

```
P0 门禁工装 ─┬─> P1 键部件（先量后改） ──┐
             └─> P2 上下文签名 ─────────┤
                                        ├─> P3 别名审计 ─┬─> P4 命中不 merge ─┐
                                        │                └─> P5 空对象冻结 ───┤
                                        │                                    ├─> 收尾
P6 命中率成因分析（全程并行，不阻塞）────┴────────────────────────────────────┘
```

排序理由（每条对应 Spec 条款）：

1. **先 P0，因为所有收益判定都靠它。** Spec §9「度量方法」要求前后交替、取中位与 95% CI，§2 说明单次带 ±50 ms 噪声；没有工装，后面每一步的「有没有效」都是猜测。
2. **P1 先于 P2，沿用 Spec §9「顺序」1→2。** 除顺序外还有独立理由：P1 只改键的构造方式，P2 改所有评估都会经过的签名路径——先做爆炸半径小的，出问题好回退。
3. **P3 必须早于 P4、P5。** P4/P5 把「每次新建对象」变成「共享对象」，风险形态是**静默数值错**（Spec §10 风险 3、4）。审计是这两步的前置闸门（Spec §5.4、§6.3），顺序颠倒就等于拿数值正确性去换速度。
4. **P5 排 P4 之后而非并行，是为了单变量归因。** 两者都落在共享分配路径上（Spec §6.1 与 §5.4 的调用面有重叠），同时改会让「节约来自哪一处」无法判断，也让回退粒度变粗。
5. **P6 全程并行，因为它不产出代码。** Spec §7 明确本期不验收它，只登记；把它塞进主链只会拖慢前三步。

## 2. 执行步骤

> 步骤号 P0–P6 只是本文的排班标签，不是产品命名。每步的「满足条款」都指向 Spec 的编号。

### P0 · 门禁与度量工装

- **做什么**：把 Spec §9 的门禁表变成一条可重复执行的命令序列；建立 A/B 交替测量方法与 signature 转储对比手段（后者取决于 Q4）。
- **动到哪**：不改产品代码。若 Q4 获准，最多新增一个**仅测试用**的转储脚本 + 必要的测试导出（先问再加）。
- **产出**：一份「跑一次即知全绿/全红」的门禁清单执行记录；本次基线数字（已实测：中位 1914 ms，总伤 53665119）。
- **满足条款**：Spec §2（基线）、§9（门禁表、度量方法）、§3 R3。
- **依赖**：无。**并行**：P6 可同时启动。

### P1 · 键部件（先量后改）

- **做什么**：先在同一 profile 下确认 `buildBuffCatalogKey` 剩余开销的构成（`teamSlotsKey` 拼装 / `bangbooKey` / `environmentBuffsKey` / 10 段 join 各占多少），再只改占比最大的那一项（D2）。
- **动到哪**：`zzz-hp/src/utils/panelBuffCalc.ts`（键构造相关函数）；必要时补 `zzz-hp/scripts/test-buff-catalog-cache.mjs` 用例。
- **产出**：一次拆分测量结论 + 一处键构造改动；对应测试全绿。
- **满足条款**：Spec §5.2、§5.3 行 2-1、§3 R4、§4.4、§9 门禁表。
- **依赖**：P0（无工装则无法归因）。**并行**：与 P2 改的文件不同、语义独立，技术上可并行，**流程上串行**（Spec §9「顺序」1→2 与单变量归因）。

### P2 · 上下文签名

- **做什么**：按 D1 落地 §4.3 的方式，消除 `eventState` 先算后查的浪费与 miss 时的重复指纹计算；签名值必须逐字节不变（Q3 决定做到 O(1) 还是 O(条数)）。
- **动到哪**：`zzz-hp/src/utils/optimalAffixAlloc.ts`（签名与记忆化区域）；`zzz-hp/src/utils/hitEvalCache.ts` 只读复用其指纹函数，不改语义；新增/扩充 `zzz-hp/scripts/test-affix-cache-key.mjs`；复用 `zzz-hp/scripts/probe-inplace-team-mutation.mjs` 作门禁用例。
- **产出**：签名路径改动 + 三条证据：（a）signature 逐字节相同；（b）就地修改仍能失效；（c）总伤不变。
- **满足条款**：Spec §4.2、§4.3、§4.4、§4.5、§3 R3/R4、§9 门禁表。

## 3. 完成标志与风险

### 3.1 每步怎么算做完

| 步骤 | 完成判据 |
|---|---|
| P0 | 门禁表可一条命令跑完并给出全绿结果；基线数字与 Spec §2 一致（总伤 53665119） |
| P1 | 键构造拆分测量有数字；改动后门禁全绿；同机交替测得可辨识的正收益 |
| P2 | signature 逐字节相同（Q4 手段就绪后）；就地修改用例仍能失效；门禁全绿 |
| P3 | 结论覆盖 §5.4 要求的全部调用点，且对 P4/P5 给出明确放行/禁止意见（Q6 边界内） |
| P4 | 命中路径不再新建 mods；门禁全绿；收益可测 |
| P5 | 各调用点读写分类完成；冻结后门禁全绿；收益可测 |
| P6 | 有成因结论与立项建议，无论结论正负 |

### 3.2 最容易出问题的三步与回退点

| 步骤 | 问题形态 | 怎么发现 | 退回到哪 |
|---|---|---|---|
| **P2** | 指纹/签名过期 → 命中旧缓存 → 数值错且**不报错** | 总伤变化；probe 用例失败；签名逐字节对比不一致 | 直接回退到 P2 前的提交（P0 基线） |
| **P4** | 共享 mods 被下游写入 → 后续评估读到脏值 | 总伤变化；单项面板比对（若 P0 有逐面板快照则更早发现） | 回退到 P4 前提交，把 P3 审计范围扩大后重做 |
| **P5** | 冻结对象被写入，非严格模式**静默失败** → 数值不动 | 总伤不变但明细异常；对拍单次评估结果 | 回退到 P5 前提交，改用「每调用点复制」而非共享 |

辅助判断：凡是「收益为正但总伤变了」一律视为失败，按 H1 回退；凡是「总伤不变但收益为 0」先怀疑测量方法（§9 度量方法），再怀疑改动。
